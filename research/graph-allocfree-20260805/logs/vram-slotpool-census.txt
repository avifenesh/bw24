# layers (that is the point of the shape). Cost is geometry-bound, layer-count-invariant.

# WHAT IT DISPLACES AT HIGH SESSION COUNTS
#     1 session  : q27   1.4 MiB   q9   1.3 MiB
#     8 sessions : q27  11.5 MiB   q9  10.5 MiB
#    32 sessions : q27  46.0 MiB   q9  42.0 MiB
#   128 sessions : q27 184.2 MiB   q9 168.1 MiB
#   pod VRAM 97887 MiB -> 0.0015% per q27 session. For scale, one q27 session's KV cache at
#   4k ctx dwarfs this; the slot pool is not a serving-density constraint at any realistic
#   session count. VRAM is NOT the reason to decline the refactor.
#
# PARKED-SESSION DECISION (freed or kept): KEEP. Justification: (1) the pool is 1.44 MiB —
# 128 parked sessions cost 184 MiB, cheaper than one 4k KV cache; (2) freeing is actively
# UNSAFE on this codebase — the captured graph BAKES slot addresses, so a freed slot returns
# to the async pool, a later live allocation lands on it, and the next replay of the parked
# session's graph writes through the stale baked pointer. That is issue #68's exact failure
# mode (lib.rs:9536 RETIRE-ON-GROW comment: "captured graphs BAKE these pool buffer
# addresses ... the next graph REPLAY writes its fa partials over them"). A parked session
# holding a live graph must hold its slots; the only safe free is dropping the graph too,
# which forfeits the reason the session was parked. (3) Freeing would also require the graph
# to be re-instantiated on unpark, paying the measured 4.2 ms instantiate + 27.4 ms warmup.
