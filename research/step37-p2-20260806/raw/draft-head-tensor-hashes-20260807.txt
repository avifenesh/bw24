=== FINDINGS
1. output.weight (3eec5831…) != blk.45.nextn.shared_head_head.weight (c90b907b…). They are
   DIFFERENT MATRICES of the same shape and dtype. The loader was reading the wrong one.
2. The three MTP blocks' heads all differ from each other (c90b907b / a22d2957 / 4b21e137) —
   each NextN block owns its own head, exactly as upstream's per-layer
   `layer.nextn.shared_head_head` lookup implies. A single shared head would have collided.
3. THE TELL: the drafter's top-level `output_norm.weight` is BYTE-IDENTICAL to the TRUNK
   artifact's (both d7526f44…), while blk.45's own `nextn.shared_head_norm.weight` is
   different (405dbb0d…). So the drafter's top-level output stack (output.weight +
   output_norm.weight) is a COPY OF THE TRUNK'S output stack, re-quantized Q6_K -> Q8_0,
   shipped so the draft gguf can stand alone. It is NOT the MTP head.
   Consequence of the old code: the MTP block's hidden was projected through the TRUNK's
   lm_head under the MTP block's OWN norm — plausible tokens, near-zero agreement with the
   trunk's actual next-token distribution => acceptance 0.
4. token_embd differs from output.weight in the drafter (139872af vs 3eec5831), so this model
   is NOT tied-embedding — another reason a head substitution cannot be waved off as benign.

=== SECOND BUG FOUND BY THE SAME PROBE (embedded-MTP loader, not this artifact's path)
`HybridModel::load`'s EMBEDDED MTP arm read `blk.{n}.nextn.shared_head.weight` — a name that
appears in NO artifact and in no upstream tensor mapping (upstream:
LLM_TENSOR_NEXTN_SHARED_HEAD_HEAD -> "blk.%d.nextn.shared_head_head"). That `load_opt` was
therefore silently always-None, so every embedded-MTP model fell back to the trunk
`self.output` in `mtp_head_forward_dev` op 12. Benign for heads genuinely tied to the trunk
head; wrong for any artifact shipping its own. Fixed to prefer shared_head_head with the old
name kept as fallback.
